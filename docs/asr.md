# Khmer ASR extension

This document describes the speech-recognition extension built on top of the
Khmer Transliteration Keyboard. The current experiment uses a pretrained
XLS-R/Wav2Vec2 CTC checkpoint and fine-tunes it for Khmer speech. It does not
train a model from scratch.

## Current experiment

- Dataset: `Digital-Divide-Data/khmer-speech-dataset`
- Model: `vitouphy/wav2vec2-xls-r-300m-khmer`
- Audio target: mono, 16 kHz WAV
- Pilot: 1,000 selected rows, split into 793 training, 81 validation, and 126 test rows
- Split policy: complete speaker groups are kept in one split to reduce speaker leakage
- Test policy: the test split is not passed to `Trainer`; it is used only for final evaluation

The older 300-row pilot in `data/voice/` remains as a small local manifest. The
1,000-row manifests are generated/materialized in Colab or Google Drive and are
ignored by Git through `data/voice_1000/`.

## Repository structure

```text
khmer_transliteration/
  asr_audio.py          # WAV decoding and 16 kHz resampling
  asr_data.py           # manifest reading and streamed HF audio replay
  asr_decoding.py       # CTC prefix beam-search experiment
  asr_inference.py      # clean tokenizer, model loading, and lazy web inference service
  asr_metrics.py        # code-point/cluster CER, Khmer WER, latency metrics
  asr_text.py           # shared transcript normalization
  romanization.py       # dictionary-backed canonical Khmer -> Romanized output

  inspect_asr_dataset.py
  build_asr_manifest.py
  validate_asr_manifest.py
  run_asr_baseline.py
  score_asr_report.py   # re-score saved predictions without loading audio/model
  finetune_asr.py
  package_kaggle_asr.py # create the Kaggle source upload bundle
notebooks/
  prepare_dataset.ipynb
  asr_baseline.ipynb
  finetune_asr.ipynb
  finetune_asr_kaggle.ipynb
kaggle/
  README.md               # 5,000-row Kaggle setup and checkpoint guidance
```

The scripts reuse the package modules. They should not import helper functions
from another command-line script.

## Environment setup

The normal keyboard environment and the ASR environment are intentionally
separate:

```powershell
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m pip install -r requirements-asr.txt
```

PyTorch is not pinned in `requirements-asr.txt` because the correct build
depends on the machine and CUDA runtime. Colab already provides a compatible
PyTorch build. For a local GPU/CPU installation, use the command generated by
the [official PyTorch installation selector](https://pytorch.org/get-started/locally/).
On Windows, run commands that calculate ASR metrics with python -X utf8 so the
neural tokenizer reads its bundled UTF-8 model files correctly.

## Dataset workflow

Inspect a small streamed sample without saving audio:

```powershell
python scripts/inspect_asr_dataset.py --max-rows 300
```

Build the pilot manifests. In PowerShell, use one line or the PowerShell
backtick for continuation; a Unix backslash is not a PowerShell continuation
character:

```powershell
python scripts/build_asr_manifest.py --target-rows 1000 --scan-rows 5000 --shuffle-buffer 5000 --output-dir data/voice_1000
```

The existing 1,000-row manifest records a shuffle buffer of 5,000. When
expanding the experiment, preserve the existing test set with the fixed-test
mode:

```powershell
python scripts/build_asr_manifest.py --target-rows 5000 --scan-rows 25000 --fixed-test-manifest-dir data/voice_1000 --output-dir data/voice_5000_fixed_test
```

This copies the original 126 test rows unchanged, excludes their speakers and
transcript groups from train/validation, and selects the remaining rows from the
same deterministic Hugging Face stream. The command infers dataset, seed,
revision, and shuffle-buffer values from the existing manifest summary. Prepare
the one-file Kaggle source bundle with:

```powershell
.\.venv\Scripts\python.exe scripts\package_kaggle_asr.py
```

Then follow `kaggle/README.md` and run `notebooks/finetune_asr_kaggle.ipynb`.

Validate the deterministic replay and WAV headers:

```powershell
python scripts/validate_asr_manifest.py --manifest-dir data/voice_1000 --output data/voice_1000/manifest_validation.json
```

The CSV manifests store metadata and source row indexes, not all audio bytes.
When training, `finetune_asr.py` replays the same deterministic stream and
materializes only the selected WAV files.

## Baseline and fine-tuning

Run a small baseline smoke test first:

```powershell
python -X utf8 scripts/run_asr_baseline.py --manifest-dir data/voice_1000 --split test --max-samples 3 --output reports/asr/baseline_smoke_test.json
```

Baseline evaluation now caches selected audio in
`data/voice_1000/audio_cache/` and prints stream/inference progress. The first
run still needs to replay the Hugging Face stream; later runs load the cached
WAV files locally. Use `--no-audio-cache` only when a fresh remote replay is
needed.

Materialize and train in a GPU notebook/runtime:

```powershell
python scripts/finetune_asr.py --stage materialize --manifest-dir data/voice_1000 --materialized-dir data/voice_1000/materialized_training
python scripts/finetune_asr.py --stage validate-tokenizer --model vitouphy/wav2vec2-xls-r-300m-khmer
python -X utf8 scripts/finetune_asr.py --stage smoke --materialized-dir data/voice_1000/materialized_training --output-dir models/khmer_xlsr_ddd_1000_clean_smoke
python -X utf8 scripts/finetune_asr.py --stage full --materialized-dir data/voice_1000/materialized_training --output-dir models/khmer_xlsr_ddd_1000_clean --checkpoint-steps 250
```

The fine-tuning script rebuilds the tokenizer directly from `vocab.json`,
checks that its full length matches the model's CTC output vocabulary, and
encodes labels with `add_special_tokens=False`. The `|` word-delimiter token
is checked before training. This prevents accidental BOS/EOS or duplicated
special-token entries from becoming training labels. The corrected checkpoint
uses the `_clean` name so the earlier pilot remains available for comparison.

Full training evaluates and saves resumable Trainer checkpoints every 250
optimizer steps, selects the lowest validation CER checkpoint, and retains at
most two checkpoint directories, including the best checkpoint. If a runtime
disconnects, restore both the output folder and the materialized training
folder, including its WAV files and manifests. Then rerun the same command with
--resume. The script checks that the model, tokenizer, and train/validation
manifests match before resuming and reports missing audio before loading the
model. Use a new output directory for a fresh run. Store both folders on
persistent storage and save a notebook version or artifact often enough to
retain recent checkpoints.

Periodic Trainer validation computes CER for checkpoint selection. Khmer-aware
WER is computed in standalone evaluation reports rather than repeatedly during
training validation.

The training script writes checkpoints only to its configured output directory.
The Colab notebook saves the materialized audio and manifests to Drive and
writes training checkpoints directly to a Drive output folder. This protects
completed checkpoint saves from a Colab runtime reset, though Drive writes may
be slower. Keep the model files needed by
`from_pretrained()` together: `model.safetensors`, `config.json`,
processor/tokenizer JSON files, and any saved training summary/checkpoints.
For a resumable cloud run, persist the complete output folder, including
checkpoint optimizer state and training_run.json, together with the complete
materialized training folder. The local model directory is intentionally
ignored by Git because the checkpoint is approximately 1.18 GiB.

The application automatically prefers `models/khmer_xlsr_ddd_1000_clean/` and
falls back to the earlier `models/khmer_xlsr_ddd_1000/` if the corrected model
has not been copied locally. Set `KHMER_ASR_MODEL_PATH` to use another local
checkpoint, or remove both local folders to fall back to the pretrained
Hugging Face model.

## Evaluation

Every reference transcript and prediction is normalized with the same NFC,
trim, and whitespace-collapse procedure before comparison. Reports include:

- cer: code-point character error rate after the documented normalization.
- grapheme_cluster_cer: Unicode grapheme-cluster edit rate, as an additional
  script-aware view. It is not the published KHCWER metric.
- wer: word error rate after reference and prediction are segmented with the
  pinned khmercut.nn tokenizer. This is an estimate because Khmer word
  boundaries can be ambiguous and the tokenizer has not been validated on the
  project's exact speech-text domain. Reports include five tokenized examples
  as diagnostics; another manual review is not required for each run.
- whitespace_wer: the old space-split WER, retained for comparison with
  earlier reports. Do not present it as the project's Khmer WER.
- sentence accuracy: exact normalized sentence matches
- mean/median/p95 model latency
- real-time factor when clip duration is available
- `[UNK]`, missing-space, and subscript-reference diagnostics

The older JSON files use the old whitespace-based wer field. Re-score their
saved predictions without downloading audio or loading the ASR model:

```powershell
python -X utf8 scripts/score_asr_report.py --report reports/asr/baseline_test.json
python -X utf8 scripts/score_asr_report.py --report reports/asr/finetuned_test_clean.json
```

The script writes new *_rescored.json files and preserves the original metrics
under previous_metrics. Keep the same test split and tokenizer version when
comparing systems. Report rates consistently as percentages in presentations;
the JSON stores rates as decimals (for example, 0.17 is 17%).

The 30-row diagnostic segmentation audit is complete. On that deliberately
selected sample, manually corrected boundaries give 43.67% WER, while automatic
`khmercut.nn` segmentation gives 50.78%. The sample combines difficult and
randomly selected examples, so neither number is an overall test-set estimate.
The audit suggests the automatic segmenter can affect WER on this domain; no
additional manual review is planned for the next training run.

On the same 126 held-out samples, the rescored pretrained baseline has 34.89%
code-point CER and 70.28% Khmer-aware WER; the clean fine-tuned model has 17.66%
CER and 46.35% WER. Neither model produced an exact full-sentence match in this
pilot. The WER comparison uses the same pinned segmenter, whose boundaries are
not fully validated for this speech-text domain. Treat these scores as pilot
estimates, not final performance claims. Re-run evaluation after model or
decoding changes and keep the test split untouched during training.

The next experiment fine-tunes on 5,000 selected rows in Kaggle, using the same
126 held-out test examples as the 1,000-row pilot. The 5,000-row target includes
the fixed test rows, and their speakers and transcript groups are excluded from
training and validation. See `kaggle/README.md` for setup and resume guidance.

WER can exceed 100% when insertions add more errors than there are reference
words. The pretrained model card's published WER/CER uses a self-split OpenSLR
test set; those results are not directly comparable with this project's
speaker-disjoint test set from Digital-Divide-Data. The new segmenter is
documented at [khmercut on PyPI](https://pypi.org/project/khmercut/). Khmer
character-cluster-aware scoring is a separate research metric; this project
reports Unicode grapheme-cluster CER as an additional measure and does not call
it KHCWER. See the [pretrained model card](https://huggingface.co/vitouphy/wav2vec2-xls-r-300m-khmer)
and the [Khmer recognition/segmentation benchmark paper](https://openaccess.thecvf.com/content/WACV2026W/VisionDocs/papers/Nom_Cross-Lingual_Transfer_for_Complex_Scripts_A_Benchmark_on_End-to-End_Khmer_WACVW_2026_paper.pdf)
for their respective protocols.

## Dual-script output

The ASR prediction is Khmer script. The current Romanized Khmer output is a
transparent dictionary-backed reverse lookup using `data/all_words.csv`: for a
known Khmer token it selects the highest-frequency existing romanization, and
it preserves unknown text. Khmer-to-Romanized text is not mathematically
unique, so this is a baseline integration rather than a fully trained
romanization model.

For the proposal, evaluate Romanized output separately with a manually
verified subset containing Khmer references and approved Romanized labels.
Do not report Romanization accuracy from automatically generated labels.

## Web API and UI

Start the application as usual:

```powershell
python -m uvicorn app:app --host 127.0.0.1 --port 8000
```

The existing keyboard endpoints remain unchanged. The ASR extension adds:

- `GET /api/asr/status` — reports whether the model has been loaded
- `POST /api/asr/warmup` — explicitly loads the model before recording
- `POST /api/asr` — accepts a WAV request body and returns Khmer text,
  Romanized text, model/device information, and inference latency

The browser UI automatically requests model warmup when the page loads, then
records microphone input, converts it to mono 16 kHz WAV, and displays both
outputs. WAV upload is supported; arbitrary WebM/MP3 conversion is
intentionally outside the current server dependencies.
